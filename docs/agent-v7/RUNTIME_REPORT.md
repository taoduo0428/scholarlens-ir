# 任务运行与恢复

## 同机模型调用并发

两个独立客户端进程分别同时提交三个研究决策请求。受控 HTTP 服务先扣住已接收的请求，再从服务端统计实际重叠的调用，最后返回可被研究网关验证的结构化决策。

|模式|同时发起|接收端并发峰值|网关限流|释放后成功|
|---|---:|---:|---:|---:|
|单进程|3|2|1|1|
|两个进程，各用进程内计数|6|4|2|2|
|两个进程，共用本地容量目录|6|2|4|2|

另由一个子进程占满两个主机的四个名额。另一个进程请求原主机和第三个主机时均被限流。强制终止持锁进程后，四个名额全部可立即重新获得。Windows 和 WSL2 的 Linux 本地文件系统均通过此项。覆盖真实供应方费用及跨主机协调还需单独验收。

运行 `python -m tools.research_eval.v7_gateway_processes --output <新文件>` 测量进程内限额，添加 `--shared` 测量同一运行卷的限额。进程终止用例为 `backend/tests/research/test_shared_capacity.py`。[进程内记录](gateway-process-results.json) · [共享卷记录](gateway-shared-results.json)

## 从 API 提交追踪到发布

提交 `b978ab8` 在新建任务的 SQLite 事务内保存已采样的 API span 标识。后台执行、工作流和综合核验接入同一条 trace。受控 HTTP 的四次模型调用、三次检索、四次来源核验和一次发布在同一条研究 trace 中完成。独立的登录 API 验收通过正常账号创建证据型任务，核对 API、后台任务和工作流的父子关系，再从同一账号的任务详情查回 trace ID。重复提交返回相同任务。

旧版库升级后可读取原任务。从另一个账号读取追踪起点时，服务返回资源不可见。验收使用本机内存导出器。部署端的远程收集和外部模型费用仍需真实环境验证。[追踪验收记录](submission-trace-acceptance.json)

## 工作进程意外退出后的接替

在一个新的 SQLite 库中，首个子进程运行真实 Worker 和本地合成语料，保存第 2 个修订和第一条证据后停在测试屏障。另一个进程尝试争用同一执行锁，服务返回 `research_worker_already_running`。积压另外三个账号的任务后，测试结束了持锁进程。新子进程重新取得执行锁，4.172 秒后全部四份报告已可读取。原任务的证据 ID 和哈希、账号下的幂等键及报告内容哈希均通过核对。四次跨账号读取都返回资源不可见。

运行 `python -m tools.research_eval.v7_worker_takeover --output <新目录>` 可复核。该实验测量 Windows 本机单活进程的接替，包含进程启动时间。[机器记录](worker-takeover.json)

## 单进程的多用户队列

在同一 SQLite 队列和一个工作进程上，分别同时提交 1、4、12 个账号的任务，核验重复提交键、完成状态、跨账号访问和备份恢复。每次试验使用独立临时目录。详情见 `tools/research_eval/v7_runtime.py` 和提交 `1cd1dfe`。

|并发用户|完成|p50 秒|p95 秒|恢复后报告哈希符合|
|---:|---:|---:|---:|---:|
|1|1/1|0.375|0.375|1/1|
|4|4/4|0.625|1.343|4/4|
|12|12/12|2.500|4.922|12/12|

命令为 `python -m tools.research_eval.v7_runtime --output <results.json>`。输入是本地受控论文，17 个任务均为零模型调用。该试验覆盖用户并发和 SQLite 恢复，长任务、外部供应方限流、跨进程分布式恢复和高负载写入仍需单独测量。当前部署按单 worker 配置。

项目看板从当前账号的任务和供应方计量记录汇总最近 50 项任务，列出已知费用、未报告费用的任务数和完成耗时。浏览器验收中，所属账号看到 1 项任务，第二个账号在同名项目中看到 0 项。模型网关还验证了单进程最多 4 次并发调用、同端点最多 2 次和异常后释放容量。

HTTP 存活探针为 `GET /healthz`，就绪探针为 `GET /readyz`。服务只在指定索引的导入元数据和 SQLite 用户表均可读时报告 ready。已测就绪、别名缺失、搜索离线和 SQLite 故障。失败响应为 503，存活探针仍可返回 200。该处不探测模型服务和向量模型。
