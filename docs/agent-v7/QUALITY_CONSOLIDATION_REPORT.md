## 个人模型执行

规划、动作用当前目标 ID，规划同时收到并校验服务器生成的节点骨架。分析提示要求少量有确切引文的评审，综合只请求已存在的陈述 ID。调用等待与 HTTP 阶段统一为最多 20 秒，并继续受任务时间限制。原先规划、分析和综合的外层等待上限为 10 秒，历史真实调用中有响应耗时超过这一上限。截断、超时、上游错误和格式错误分别处理。对运维已配置的可信 HTTPS 基址和 `deepseek-v4.1-flash` Chat Completions 请求，发送 JSON 模式和关闭 thinking 的参数，以把有限输出预算留给完整的结构化结果。其他模型和 Responses 使用原传输协议。模型输出仍须通过严格 Schema、作用域和证据检查。

| 执行验收 | 基线 | 候选版本 |
| --- | --- | --- |
| 受控 HTTP 的规划、决策、分析、综合 | 4/4 | 4/4，4 次调用，4 份回执，未回退 |
| 真实供应商的同一双论文任务 | 4 次尝试，3 次 HTTP 200，四个阶段均未达标 | 0 次请求，当前进程缺少模型基址、模型名和 API Key，修复效果待真实调用确认 |

候选受控任务同时通过检索、报告发布与双论文综合检查，7 条直接陈述有出处。新增回归确认白名单外不发送供应商专用参数、输出上限仍然生效、截断的 JSON 即使可解析也拒绝。真实供应商本轮没有可用回执或费用。历史记录见 [真实模型基线](live-research-acceptance.json)。

## 收敛与兼容性

字段验真后直接复用同一份研究档案，消除一次发布流程中重复的档案构建，原 `evaluate()` 的返回契约保持兼容。归并重复的规划骨架。PDF 依赖文件移除两条重复的版本声明，版本来源统一到现有锁和约束，`uv pip compile` 完成解析。审计覆盖解析后的 83 个包。真正参与 LangGraph 检查点、PDF 解析、HTTP 和追踪的依赖仍按其现有版本使用。

## 工程验收

- 后端在独立 Elasticsearch 8.19.23 副本与隔离账号环境集中运行，**918 项通过，0 失败，0 跳过**。副本含 859 篇论文、49,420 条向量，源索引签名一致，验收端口全部关闭。第一次直跑遇到旧测试的固定 9200 端口和 Windows Git 环境问题。随后启动副本时又遇到 Java 不能从中文路径附加 ES entitlement JAR。使用项目的隔离验收入口和 ASCII 路径的现有 ES 安装完成正式运行。
- 前端 **47 项通过**，结构、TypeScript 和启用研究入口的 API 模式生产构建通过。初次构建沿用了默认功能开关，研究表单不可用。按现有 Docker 配置打开研究开关重建后，Chrome 157 在 `127.0.0.1:18012` 实测注册、登录、真实论文检索、提问、打开报告、定位 5 处原文和导出 Markdown。6,278 字节的下载内容与页面原稿一致，报告提示证据不足，页面错误 0，匿名读取返回 401。
- Ruff、Git diff 格式与 Gitleaks 补丁检查通过。解析后的 83 个 Python 包与前端锁文件均报告 0 项已知漏洞。Docker 配置保留，Windows 和 WSL 可用路径未发现容器 CLI，本轮无镜像重构建和系统包复扫记录。
- 改动和报告保存在当前本地分支。远端提交和既有工作台对应上一版。
